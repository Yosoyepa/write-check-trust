## 3. MVP fijado

Una raíz de **negocio** y un paquete Python regular por instancia. El prefijo
de paquete puede ser anidado si se resuelve a su ruta real y se califica; no se
acepta usar el nombre punteado como un directorio literal. Harness, tests y
dependencias de verificación tienen inventarios propios: no constituyen otro
paquete de negocio ni una promesa de soporte monorepo.

| Caso | Raíz / paquete propuestos | Objetivo y límite |
|---|---|---|
| Layout A | `src` / `shop` | Roles de SPEC-B3-01; contratos separados de casos de uso cuando un módulo se clasifica como `ports` |
| Layout B | `python` / `commerce` | `core.entities`, `core.contracts`, `core.usecases`, `api`, `infrastructure`, `bootstrap`; misma tabla de aristas que A |
| Brownfield | `src` / `personal_assistant` en [personalAssistant](https://github.com/Yosoyepa/personalAssistant), elegido por el usuario durante este turno | Candidato al SHA `c1beefe5118ed5cb87a5f3545490aa2360831426`; 201 `.py` en src. Inventario/roles/deuda por revisar, sin renombres o cambios de bytes durante plan |
| Compatibilidad local | `src` / `example` en beta.2 | Control de regresión real del template; **no sustituye** un repo brownfield representativo externo |

Los nombres A/B son ejemplos de fixtures, no convenciones exigidas. Los paquetes
contenedores y `__init__.py` también requieren disposición; no se pierde el
root del paquete al contar solo hojas. Un contenedor sin lógica puede tener
exclusión explícita de rol, pero sus imports/reexports siguen inventariados.
Un módulo con lógica de dos roles exige decisión: no se divide automáticamente.
No se promete clasificación de símbolos arbitraria dentro de un módulo.

Se conserva el grafo concreto de seis roles de SPEC-B3-01. Los roles no usados
pueden estar vacíos si el recorrido lo permite (p. ej. CLI en composición); el
paquete total y cada capacidad requerida no pueden estar vacíos. `ports` es un
rol lógico de módulos de contratos, no una carpeta obligatoria. Un Protocol
co-localizado con su caso de uso, como InventoryRepository en beta.2, conserva
su módulo de aplicación y se registra como símbolo de puerto: no se reclasifica
todo el módulo como `ports`. Una importación desde adapters.out a un módulo
mixto de aplicación no obtiene una excepción silenciosa por importar un solo
símbolo; puede quedar en compatibilidad/shadow hasta decisión del mantenedor.

Se prueba un puerto de inventario con `get(product)` / `save(inventory)`,
propiedad de la aplicación, y el caso de uso de reserva ya existente. Reusar
Inventory/ReserveStock/MemoryInventoryRepository; un segundo adaptador local
de prueba basado en SQLite es candidato para demostrar sustitución, sin nueva
dependencia ni servicio de producción. El molde no genera esas implementaciones.

Contrato propuesto del fixture: con producto P y stock S, reservar Q positiva
y Q≤S devuelve y persiste S−Q; otra lectura observa ese valor; un producto
distinto no cambia. Q≤0 o Q>S produce el error de dominio acordado y conserva
el estado. Para el adaptador persistente, reabrir el almacén conserva la reserva.
Misma suite contra ambos; negativos: doble descuento, retorno correcto sin
persistir y modificación de otro producto. Una ruta CLI real debe mostrar S−Q.
No se promete idempotencia, reservas concurrentes ni atomicidad distribuida.
La equivalencia de tipos por sí sola no aprueba este contrato.

Fuera del MVP: varias raíces/paquetes de negocio, namespace packages sin
calificación, plugins ejecutables, múltiples contextos/arquitecturas, análisis
general de imports dinámicos y efectos externos de producción. El perfil nuevo
debe devolver alcance no soportado/incompleto; no medir solo la primera raíz.
